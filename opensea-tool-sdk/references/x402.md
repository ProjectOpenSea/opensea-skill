# x402 Payment-Gated Tools (Pay-per-Call)

x402 is the HTTP 402-based pay-per-call protocol used by tools that charge USDC per invocation. The caller signs an EIP-3009 `TransferWithAuthorization` and the server settles after executing the tool.

## How x402 works

```
Agent                        Tool Server                   Facilitator
  |--- POST /api ------------->|                                |
  |<-- 402 + requirements -----|                                |
  |                            |                                |
  |  (sign EIP-3009 USDC       |                                |
  |   TransferWithAuthorization)|                               |
  |                            |                                |
  |--- POST /api ------------->|                                |
  |    X-Payment: <base64>     |--- POST /verify -------------->|
  |                            |<-- { isValid: true } ----------|
  |                            |                                |
  |                            |  (execute tool handler)        |
  |                            |                                |
  |                            |--- POST /settle -------------->|
  |                            |<-- { success, txHash } --------|
  |<-- 200 + result -----------|                                |
```

1. Agent calls the tool endpoint without payment
2. Server returns `402` with `accepts[]` containing payment requirements (amount, asset, recipient, network)
3. Agent signs an EIP-3009 `TransferWithAuthorization` for the requested USDC amount
4. Agent retries the request with the signed payload in the payment header
5. Server verifies the payment via the facilitator's `/verify` endpoint
6. Server executes the tool handler
7. Server settles the payment via the facilitator's `/settle` endpoint
8. Server returns the result

### Protocol versions: v1 vs v2

x402 has two wire formats, and `pay`/`paidFetch` handle both transparently — but if you implement the flow yourself, the difference matters:

| | Challenge location | Payment header | Payload envelope |
|---|---|---|---|
| **v1** | `402` response **body** (`{ accepts: [...] }`) | `X-PAYMENT` | `{ x402Version, scheme, network, payload }` |
| **v2** | `PAYMENT-REQUIRED` response **header** (base64) | `PAYMENT-SIGNATURE` | `{ x402Version, payload, resource, accepted }` |

The version is advertised by the challenge's `x402Version`. The `network` may be a short name (`base`) or CAIP-2 (`eip155:8453`), and the amount field is `maxAmountRequired` (v1) or `amount` (v2). Sending a v1 `X-PAYMENT` to a v2 server (or vice versa) makes the server silently re-issue its `402`.

## Build a tool with x402 paywall (server side)

Use `defineToolPaywall` to keep the manifest price and the gate's enforced price in sync:

```typescript
import { createToolHandler, defineToolPaywall, defineManifest } from "@opensea/tool-sdk"
import { z } from "zod/v4"

// 1. Define paywall config (single source of truth for price)
const paywall = defineToolPaywall({
  recipient: "0xYOUR_WALLET_ADDRESS",  // where USDC is sent
  amountUsdc: "0.01",                  // price per call in USDC
  // network: "base",                  // default: "base" (or "base-sepolia" for testnet)
  // facilitator: "payai",             // default: "payai" (or "cdp" for Coinbase)
})

// 2. Include pricing in the manifest
const manifest = defineManifest({
  name: "My Paid Tool",
  description: "A tool that costs $0.01 per call",
  endpoint: "https://my-tool.example.com/api",
  creatorAddress: "0xYOUR_WALLET_ADDRESS",
  inputs: { type: "object", properties: { query: { type: "string" } }, required: ["query"] },
  outputs: { type: "object", properties: { result: { type: "string" } } },
  pricing: paywall.pricing,  // advertised in manifest
})

// 3. Add the gate to the handler
export const toolHandler = createToolHandler({
  manifest,
  inputSchema: z.object({ query: z.string() }),
  outputSchema: z.object({ result: z.string() }),
  gates: [paywall.gate],     // enforced at runtime
  handler: async (input) => ({ result: `Paid result: ${input.query}` }),
})
```

### Facilitator options

| Facilitator | Function | Auth required | Best for |
|-------------|----------|---------------|----------|
| PayAI | `payaiX402Gate()` | No | Prototyping, free to use |
| Coinbase CDP | `cdpX402Gate()` | Yes (JWT via `createAuthHeaders`) | Production |

For lower-level control, use `payaiX402Gate()` or `cdpX402Gate()` directly instead of `defineToolPaywall()`.

### A failed settlement withholds the output

The handler runs **before** `/settle`, so payment can fail after the work is already done. When that happens the SDK logs the failure and returns `502` without the output. The caller was not charged, so a `502` is the honest answer: you eat the handler's cost for that call, and a retry pays and succeeds.

Two consequences you must still design for:

1. **A failed settlement costs you the handler's work.** If your handler is expensive, that cost is unrecoverable even though nothing is given away.
2. **One authorization can produce several paid responses.** `/verify` is stateless, and the facilitator only detects a spent nonce once it is onchain (it simulates `transferWithAuthorization` and reads `authorizationState`). So N concurrent requests carrying the *same* payment header all verify, all run the handler, and only one settlement can ever land; the rest fail. Retrying those failures never helps: the nonce is spent. `settlement: "required"` denies those callers the output, but they still consumed your handler, so use a `replayGuard` to reject them earlier.

Opt out with `settlement: "best-effort"` to return the output with a `200` even when settlement fails:

```typescript
export const toolHandler = createToolHandler({
  manifest,
  inputSchema,
  outputSchema,
  gates: [paywall.gate],
  settlement: "best-effort",   // default: "required" (502, output withheld)
  handler: async (input) => ({ result: `Paid result: ${input.query}` }),
})
```

Use `"best-effort"` only if you reconcile failed settlements out-of-band and can absorb the ones you never recover. A settlement that failed because the nonce was already spent can never be reconciled.

### Enforce single-use authorizations with `replayGuard`

The default `settlement: "required"` stops free output but still lets N concurrent replays each run your handler. To reject replays *before* the handler runs, pass a `replayGuard` backed by storage shared across all your instances:

```typescript
import { Redis } from "@upstash/redis"

const redis = Redis.fromEnv()

const paywall = defineToolPaywall({
  recipient: "0xYOUR_WALLET_ADDRESS",
  amountUsdc: "0.01",
  replayGuard: {
    // Atomic claim: SET NX returns null when the key already exists.
    // The TTL must outlast the authorization, or a replay arriving after
    // expiry claims the key again.
    reserve: async key =>
      (await redis.set(key, "1", { nx: true, ex: 3600 })) !== null,
    // Optional: called only when the facilitator provably never broadcast a
    // transaction (a 429), so the caller can retry with the same signature.
    release: async key => {
      await redis.del(key)
    },
  },
})
```

The key is the `(payer, nonce)` pair scoped by network and asset, which is the same identity the token contract treats as single-use. A claimed authorization gets a `402` with `error: "payment_authorization_already_used"`.

Requirements:

- **`reserve` must be atomic** (Redis `SET NX`, Cloudflare KV/D1 compare-and-set, a unique index in Postgres). A read-then-write is itself racy.
- **Storage must be shared across instances.** An in-process `Set` protects one instance and gives no protection at all on serverless, where concurrent requests land in separate isolates.
- **Expire entries, but not too early.** The TTL must cover the longest `validBefore` window you accept: the token contract will honor the authorization until then, so a key that expires first lets a late replay claim it again. Callers choose their own `validBefore`, so pick a TTL from the ceiling you are willing to accept rather than from how long a request takes.
- **`reserve` may fail closed.** If it throws (store outage), the gate logs and returns the same `402` as a real replay. An outage cannot be distinguished from a replay, and guessing "not a replay" is the expensive guess. This couples your tool's availability to the store: while it is down, paid calls are refused.
- **An ambiguous settlement failure keeps the claim.** `release` runs only for a failure that proves nothing was broadcast (a facilitator 429). A timeout, a socket error, or a 5xx can all arrive after the facilitator already broadcast `transferWithAuthorization`, and releasing while that transaction is pending would reopen the replay window the guard exists to close. Those claims expire with the TTL instead.
- **A failing handler burns the authorization.** The claim is made before the handler runs and is not released if the handler throws, so that caller must sign a new authorization to retry. Releasing there would hand anyone who can make your handler fail an unlimited number of handler runs for one signature.
- **Both calls are capped at 2s.** A store that hangs would otherwise stall the response, so a timeout counts as a failure: `reserve` fails closed, and a `release` timeout is logged without masking the settlement error.

`replayGuard` is also available on `payaiX402Gate()`, `cdpX402Gate()`, and `paidPredicateGate()`. It is off by default because the SDK cannot provide shared storage portably, but for any tool whose handler is expensive to run, configure one.

## Call an x402-paid tool (agent/client side)

### Via CLI

```bash
# POST tool (params in a JSON body) — the default
PRIVATE_KEY=0x... npx @opensea/tool-sdk pay \
  https://my-tool.example.com/api \
  --body '{"query": "hello"}'

# GET tool (params in the query string) — pass --method GET
PRIVATE_KEY=0x... npx @opensea/tool-sdk pay \
  "https://my-tool.example.com/search?words=tiny%20dinos&from=someuser" \
  --method GET
```

`pay` probes for the `402`, signs the EIP-3009 authorization, and retries with the version-correct payment header (handles x402 v1 and v2). Useful flags:

- `--method <GET|POST|PUT|PATCH|DELETE>` — defaults to `POST`. Bodyless verbs (GET/HEAD/DELETE) put params in the query string, not `--body`. If a POST probe 404/405s and no method was set, `pay` auto-retries as GET.
- `--max-amount <baseUnits>` — refuse to sign if the server asks for more (default 10 USDC / `10000000`; `unlimited` to disable). It also rejects burn/zero recipients and non-USDC assets before signing.
- `--wallet-provider <privy|turnkey|fireblocks|bankr|private-key>` — use a managed wallet instead of `PRIVATE_KEY`. `RPC_URL` defaults to a public Base endpoint when unset.

### Via SDK: `paidFetch`

```typescript
import { paidFetch, createWalletFromEnv } from "@opensea/tool-sdk"

const adapter = createWalletFromEnv()  // reads PRIVATE_KEY from env

const res = await paidFetch("https://my-tool.example.com/api", {
  signer: adapter,
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ query: "hello" }),
  // Safety guards:
  maxAmount: "100000",             // max 0.10 USDC (in 6-decimal base units)
  allowedRecipients: ["0x..."],    // only pay this address
})

const data = await res.json()
```

`paidFetch` automatically:
1. Makes the initial request
2. Parses the 402 response for payment requirements
3. Validates requirements against your safety guards (`maxAmount`, `allowedRecipients`, `allowedAssets`)
4. Signs the EIP-3009 `TransferWithAuthorization`
5. Retries with the version-correct payment header (`X-PAYMENT` for v1, `PAYMENT-SIGNATURE` for v2)

### Via raw HTTP (any language)

```
POST /api HTTP/1.1
Host: my-tool.example.com
Content-Type: application/json

{"query": "hello"}
```

If the response is `402`, read the payment requirements from `body.accepts[0]` (v1) or the base64 `PAYMENT-REQUIRED` response header (v2), sign the USDC transfer authorization, base64-encode the payment payload, and retry with the matching header — `X-PAYMENT` (v1) or `PAYMENT-SIGNATURE` (v2). See "Protocol versions" above for the envelope shapes.
